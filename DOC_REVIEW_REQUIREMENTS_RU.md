# Требования к электронному ревьюверу документации YDB

Статус: версия 0.2 от 8 октября 2026 года. Заказчик прочитал требования без
возражений; схема обновления CI уточнена: использовать передвигаемый тег.
Заказчик: iuriisintiaev. Проверяемый репозиторий: `ydb-platform/ydb`.
Рекомендуемый репозиторий реализации: `ydb-platform/ydbdoc-review-ng`.

Документ описывает новый режим `doc_review`. Действующий контракт перевода
`REQUIREMENTS_RU.md` в ydbdoc-review-ng относится к `doc_translate`, `doc_verify`
и `doc_continue`. Требования нового режима не изменяют этот контракт.
Подтверждённые сведения о CI и коде приведены в [банке знаний](knowledge/doc-review/INDEX.md).

## 1. Цель и границы проекта

После создания PR с изменениями документации ревьювер проверяет соблюдение
правил проекта и публикует объяснимые замечания на русском языке. Для автора
из проекта проверка начинается автоматически. Для внешнего автора платный
запуск ожидает разрешения сопровождающего. Повторный запуск вызывается меткой
`doc_review`. Проверка выполняется в Docker и прекращается при исчерпании
настраиваемого бюджета одного запуска.

| ID | Обязательное требование из запроса |
|---|---|
| U-01 | Автоматическая проверка PR, изменяющих документацию |
| U-02 | Автозапуск для участников проекта; внешний автор ожидает разрешающей метки |
| U-03 | Использование правил из PR #55451 и их нормативных источников |
| U-04 | Выполнение проверки в Docker |
| U-05 | Модель такая же, как в `doc_translate` |
| U-06 | Учёт расходов одного запуска и остановка при превышении порога из переменных |
| U-07 | Ручной перезапуск меткой `doc_review` |
| U-08 | Код вне ydb; требования и банк знаний в отдельном репозитории |

Уточнение U-02: фактическая разрешающая метка в изученном CI называется
`ok-to-test`. Написание `ok-2-test` в запросе считаем ссылкой на эту существующую
метку; создание второй метки требует отдельного решения.

Предлагаемая первая версия выдаёт замечания и GitHub suggestions без коммитов
в ветку автора и без автоматического блокирования merge. Это предложение
подлежит согласованию, как и обработка draft PR. Автоматическая проверка каждого
нового head после пяти минут ожидания согласована заказчиком.

## 2. Размещение и версионирование

**R-01.** Рекомендуется развивать ydbdoc-review-ng: общие GitHub/Yandex/YDB
адаптеры уже находятся там. Для проверки правил создать самостоятельную
команду `review`, отдельную оркестрацию и пакет `policy_review/`. Режимы перевода
и проверки правил должны иметь раздельные политики допуска и бюджетирования.

Предлагаемая структура:

```text
ydb-platform/ydbdoc-review-ng/
  DOC_REVIEW_REQUIREMENTS_RU.md
  knowledge/doc-review/
    INDEX.md
    sources.md
    current-ci.md
    decisions.md
    open-questions.md
  src/ydbdoc_review_ng/policy_review/
  .github/actions/policy-review/
  docker/Dockerfile.policy-review
  tests/policy_review/
```

**R-02.** В ydb остаётся небольшой workflow `.github/workflows/ydbdoc-policy-review.yml`:
события, проверка допуска, передача параметров, запуск доверенного action и
публикация результата. CI ссылается на постоянный передвигаемый тег action
в репозитории реализации, например
`ydb-platform/ydbdoc-review-ng/.github/actions/policy-review@doc-review-stable`.
Точное имя тега определяется при внедрении и затем остаётся постоянным.

Новые версии выпускаются добавлением коммитов в репозиторий реализации и
переносом этого тега на подготовленный коммит. Обновление ревьювера не требует
изменения consumer workflow в ydb или его повторного согласования: изменения
CI долго аппрувятся. Не фиксировать в consumer workflow commit SHA action
или digest образа, которые пришлось бы менять при каждом выпуске.

Контейнер собирать в репозитории реализации и публиковать в GHCR до переноса
тега action. Соответствующий коммит action определяет образ своей версии
и может фиксировать его digest внутри action, вне consumer CI. После переноса
тега следующий запуск использует обновлённый action и соответствующий образ;
не требуется отдельное обновление ссылки на контейнер в ydb. Кэш не должен
оставлять предыдущую версию при новом запуске через тот же тег.

В начале запуска сохранять фактически разрешённые action commit SHA и image
digest для аудита и воспроизводимости. Уже начавшийся запуск продолжает
работать с выбранной версией. Для отката перенести тот же тег на предыдущий
рабочий коммит с доступным образом. Создание и перенос тега выполняются
уполномоченными сопровождающими репозитория реализации. Первоначальное
добавление workflow и изменения его интеграционного контракта остаются
отдельными изменениями CI.

**R-03.** Правила документации остаются канонически в ydb. В банке знаний
хранить ссылки, происхождение правил и принятые решения по ревьюверу.
Копии правил допускаются только как явно версионированные тестовые fixtures,
не как второй редактируемый источник. Полные запросы/ответы модели, секреты
и рабочие отчёты PR не включать в публичный репозиторий.

Смысл «отдельного репозитория» требует уточнения: отдельный от ydb или также
отдельный от кода. До ответа вариант выше является рекомендацией.

## 3. События, допуск и перезапуск

**E-01.** Предлагаемый набор событий: `pull_request_target` с типами `opened`,
`reopened`, `synchronize`, `ready_for_review`, `labeled`, `closed` и
`converted_to_draft`. Последние два служат для остановки устаревшего запуска.
Платный этап запускается только для открытого PR с подходящими изменениями.
Предлагается пропускать draft до `ready_for_review`; поведение требует согласования.

**E-02.** Scope определяется по полному списку изменённых файлов PR с пагинацией.
Начальная область: `ydb/docs/**`. Изменения вне документации не запускают модель.
Markdown/YFM, TOC, includes и изображения классифицируются отдельно. Изменения
только инфраструктуры документации или правил дают явный результат «нет контента
для проверки», если не затрагивают проверяемые страницы. PR с кодом и документацией
проверяется по документационной части.

**E-03.** Для определения участника проекта использовать тот же смысл допуска,
что в `pr_check.yml`: автор является владельцем репозитория либо GitHub API
подтверждает его статус collaborator. Проверять автора PR, а для ручных меток
также пользователя, поставившего метку. Staff login не является GitHub login.
Автор из fork может быть участником проекта. Значение `author_association`
и расположение ветки сами по себе не заменяют API-проверку.

Ошибка API доступа не трактуется как разрешение. В таком случае платный запуск
не начинается, публикуется понятная диагностика инфраструктурной ошибки.

**E-04.** Для внешнего автора `ok-to-test`, поставленная пользователем с
разрешёнными правами, разрешает ревью конкретного `head_sha`. До разрешения
нет вызовов модели; отображается ожидание. Предлагается повторное разрешение
после каждого изменения head. Доверие на весь PR является альтернативой для согласования.

**E-05.** Разрешение сохранять как `(repository, PR, head_sha, label_event_id,
approver, approved_at)`. Обработчик использует payload события и проверенное
происхождение метки. Перед запуском сверяет актуальный head. Другой CI удаляет
`ok-to-test`, поэтому нельзя требовать её наличия в актуальном списке меток,
если разрешение на этот SHA уже принято. Ревьювер не удаляет общую `ok-to-test`.

**E-06.** Добавление `doc_review` пользователем с разрешёнными правами вызывает
новую попытку на актуальном head. Метка не обходит допуск внешнего автора.
Для ранее разрешённого SHA достаточно сохранённого разрешения. Принятая
`doc_review` снимается, чтобы её можно было поставить повторно; при отказе
метка также снимается с объяснением, если есть право на эту операцию.
Начальный вариант разрешает ручные команды collaborators с правом `write`,
`maintain` или `admin`; конкретная политика согласуется.

**E-07.** Нерелевантные метки не вызывают модель и не отменяют текущую проверку.
События допуска, удаления командной метки и публикации отчёта не образуют цикл
повторных запусков. Для повторно доставленного события действует идемпотентность.
Ручной повтор на том же SHA получает новый номер попытки и отдельный бюджет.

**E-08.** Автоматически проверять каждый новый head PR, удовлетворяющий допуску,
после 300 секунд без следующего изменения head. Новый `synchronize` отменяет
ожидание старого head и начинает полное ожидание нового. Для серии коммитов
проверяется только последний head после пяти минут тишины. Интервал считается
по получению/обработке события GitHub, не по author/committer timestamp коммита:
эти даты задаются автором и не определяют время push. Очередь runner может
увеличить задержку; гарантировать запуск ровно через пять минут нельзя.

Ожидание выполняется лёгким доверенным шагом до подготовки snapshot,
запуска Docker и платных запросов. Устаревшая попытка завершается как
`superseded`, без вызовов модели. Перед платным этапом повторно проверить
актуальный head, статус PR и допуск именно этого SHA. Изменение head не
переносит на него разрешение предыдущего head внешнего автора.

Одновременно выполняется не более одного платного ревью одного PR.
Группа `concurrency` включает repository и PR number, имеет отдельное имя
для ревьювера и `cancel-in-progress: true`. События фильтруются до постановки
в эту группу: нерелевантная метка не отменяет полезную работу. Ручной повтор
через `doc_review` также проходит этот механизм ожидания и допуска.

Если новый head появляется после старта платного этапа, предыдущая попытка
останавливается, её расходы/резервы сохраняются. Задержка объединяет быстрые
коммиты до старта, но не исключает обновления уже запущенного ревью. Новый
Docker worker не начинает платные вызовы, пока предыдущий не остановлен;
блокировка/lease в постоянном хранилище обеспечивает это и при задержке отмены
GitHub Actions. Отчёт привязан к проверенному head. Перед публикацией повторно
проверяется актуальность head; устаревший результат не выдаётся за проверку
последней версии. Закрытие PR останавливает работу.

## 4. Загрузка и применение правил

**P-01.** Начальная точка правил: `ydb/docs/.ruler/DOCUMENTATION_POLICY.md` из
PR #55451. Она требует полностью прочитать, в указанном порядке:
`GENERAL_RULES.md`, `FORMAT_RULES.md`, `DOCUMENTATION_RULES.md`.
Все пути разрешаются относительно `ydb/docs/.ruler/`. При конфликте более
поздний нормативный файл имеет приоритет. Workflow не переопределяет эти правила.

**P-02.** Предлагается брать policy и нормативные файлы с зафиксированного
доверенного `base_sha`, контент с `head_sha`, старую версию с `merge_base_sha`.
Запуск не использует изменённые самим PR правила для ослабления его проверки.
До слияния #55451 требуется отдельно утвердить фиксированный rules SHA или
дождаться появления policy в целевой ветке. Молчаливого fallback к произвольным
правилам не должно быть. SHA и хеши полного набора правил сохраняются в аудите.

**P-03.** Читать целиком изменённые страницы и ограниченный связанный контекст:
includes, glossary, цели ссылок/якорей и TOC. Новые страницы проверяются целиком.
Для существующих страниц предлагается публиковать нарушения, введённые или
существенно затронутые PR; прежние проблемы отделять от новых. Это область для
согласования. Удалённые страницы проверять по последствиям удаления ссылок/TOC.
Переименование с изменением текста учитывать как обе операции.

**P-04.** Предлагаемая начальная языковая область: RU и EN. Русские правила
применять к содержанию обеих локалей с учётом языка статьи, не требовать
автоматического перевода. Комментарии ревьювера всегда на русском языке.

**P-05.** Проверять все правила 1–15, сохраняя исходные номера и приоритеты:
критические 3, 7, 8; высокие 1, 2, 6, 9, 14; средние 4, 5, 10, 11, 12;
низкие 13, 15. Дополнительно учитывать GENERAL_RULES и FORMAT_RULES.
Coverage для каждого применимого правила: `checked`, `not_applicable`,
`not_checked` с причиной. Непроверенное правило не считается соблюдённым.

**P-06.** Формальные проверки выполнять кодом, когда результат воспроизводим:
MD032, MD009, язык fenced SQL-блоков `yql`, существование файлов и якорей,
поддерживаемая YFM-разметка. Семантические проверки выполнять моделью с полным
нормативным контекстом. Правило 15 требует определить область запрещённого тире;
нельзя автоматически считать нарушением дефисы Markdown, код и CLI-флаги.

**P-07.** Для правила 13 требуется визуальное сравнение изображений. Изученный
модельный адаптер передаёт текст: полную проверку стиля изображений с ним нельзя
считать реализованной. В первой версии отображать `not_checked` и основание,
либо отдельно согласовать мультимодальный механизм. Для правила 8 отделять
статический анализ примеров от реального выполнения кода: примеры PR не исполняются
в среде с секретами. Недоступная техническая информация не заменяется догадкой.

**P-08.** Замечание содержит `rule_id`, приоритет, полный путь от корня ydb,
позицию в проверенном файле при её наличии, цитату, объяснение нарушения и
предложение исправления. Вывод модели проверяется по схеме, пути и цитате.
Несуществующие строки, пути и неподтверждённые цитаты не публикуются как факты.
Неуверенные рекомендации отделяются от подтверждённых нарушений.

**P-09.** GENERAL_RULES требует автоматического исправления грамматики и
орфографии. Применение этого правила к боту требует решения заказчика:
suggestions без коммита либо автоматические коммиты. Черновик предполагает
suggestions и явно фиксирует это расхождение до согласования; цитируемый контент
PR не может сам предоставить боту право записывать в ветку.

## 5. Docker, модель и изоляция

**T-01.** Платный анализ выполняется в Docker-образе из доверенного репозитория
реализации. Образ содержит фиксированные версии runtime и зависимостей;
сборка на каждом PR не требуется. Документация монтируется как данные только
для чтения, результаты пишутся в выделенный каталог.

**T-02.** Не исполнять скрипты, Git hooks, конфигурацию сборки, расширения
Diplodoc, инструкции AGENTS/SKILL или shell из проверяемого PR. Секреты
доступны только доверенному коду. Model worker получает API модели и
минимальный доступ к аудиту, publisher отдельно получает GitHub write token.
Не передавать токен записи GitHub в prompt или в недоверенные данные.

**T-03.** Для `doc_review` использовать тот же provider, URI модели и
параметры reasoning, что у production `doc_translate`. На исследованном
срезе модель в runtime задана как `deepseek-v4-flash`, provider Yandex Cloud,
endpoint OpenAI-compatible. Рекомендуется общий реестр конфигурации обоих
режимов, без независимых расходящихся значений по умолчанию. Не переключать
ревью на другую модель при ошибке без явной конфигурации и согласования.

**T-04.** Ограничивать время запуска, HTTP timeout, число попыток, число и
размер файлов, размер контекста и output tokens. Превышение лимита или
неполный список файлов вызывает явный неполный/ошибочный результат.
Не обрезать файлы или правила молча. Ошибки 429/5xx допускают ограниченные
повторы только после проверки остатка бюджета.

**T-05.** Из-за контекста `pull_request_target` итоговый GitHub Check создаётся
явно на проверенном `head_sha`, а не только на SHA workflow. Права нового
workflow: `contents: read`, `pull-requests: write`, `issues: write`,
`checks: write` по необходимости. Токен для проверки членства применяется
в отдельном шаге допуска и не передаётся модели. Если автоматические правки
будут согласованы, права записи контента добавляются отдельно.

**T-06.** Workflow, реагирующий на PR документации, и его finalizer размещать
в `ydb-platform/ydb/.github/workflows/`. Сборку worker image размещать рядом с кодом
в `ydbdoc-review-ng`. До готовности image, audit schema, stable tag и источника
правил новые jobs отключены: `YDBDOC_REVIEW_ENABLED` в ydb отсутствует или равна
`false`. Значение ровно `true` включает jobs без изменения CI; бюджет сам по себе
не включает проверку. Установка CI в main ydb выполняется через PR и проверки
защищённой ветки, без обхода repository rules.

## 6. Учёт расходов и отмена

**B-01.** Обязательная переменная: `YDBDOC_REVIEW_MAX_RUN_COST_RUB`.
Значение задаётся в GitHub Actions Variables проверяемого репозитория,
валюта RUB, конечное неотрицательное число Decimal. Пустое, отрицательное,
NaN или некорректное значение запрещает платный запуск с диагностикой.
Ноль означает отключение платных вызовов. Числовой порог задаёт заказчик. На момент внедрения через GitHub API проверено
текущее значение repository Variable в ydb: `5000` RUB. Это настройка репозитория,
а не default реализации.

Создать в **ydb-platform/ydb**, где выполняется consumer workflow:
`Settings → Secrets and variables → Actions → Variables → New repository variable`.
Name: `YDBDOC_REVIEW_MAX_RUN_COST_RUB`. Value: сумма на один запуск в рублях,
например `50` (пример, не утверждённый бюджет). Дробное значение записывать
через точку, например `12.50`. Это несекретная Variable; ключ модели хранится
отдельно в Secrets. Consumer передаёт `${{ vars.YDBDOC_REVIEW_MAX_RUN_COST_RUB }}`
доверенному action и далее в одноимённую переменную окружения worker. Переменная
в репозитории реализации не становится автоматически доступна workflow в ydb.
Изменение суммы в Settings не требует изменения файла CI.

Инструкция GitHub: [Repository configuration variables](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables#creating-configuration-variables-for-a-repository).

**B-02.** Все платные попытки одного запуска, включая повтор после ошибки,
восстановление невалидного JSON и дополнительные проверки, входят в одну сумму.
Для каждой попытки сохранять ID, run/attempt ID, PR, head SHA, модель и
версию тарифов, usage, стоимость, время и причину завершения.
Денежные расчёты выполнять Decimal; округлять только отображение.

**B-03.** Если provider возвращает billable cost, использовать его. Иначе
считать по фактическому usage и версионированным тарифам input, cached input,
output и reasoning согласно контракту provider. Cached input не учитывать
дважды; reasoning не добавлять второй раз, если он уже включён в output.
Тарифы из текущего кода переводчика являются его конфигурацией, а не
подтверждением актуальных тарифов провайдера.

**B-04.** Проверять бюджет перед каждой HTTP-попыткой, включая внутренний retry
адаптера. После ответа немедленно прибавлять фактическую сумму. При
`spent >= limit` больше не начинать платных вызовов. При `spent > limit`
завершать ревью с причиной `budget_exceeded`, сохранять частичный отчёт и
расход. Такой запуск не является успешно завершённой проверкой всех правил.

**B-05.** Чтобы ограничить возможное превышение уже начатым запросом,
до отправки резервировать консервативную верхнюю стоимость input плюс
максимального output. Input оценивать верхней границей; cached discount
не учитывать заранее. Если резерв не помещается в остаток, не начинать
запрос и завершить с `budget_insufficient`. После ответа сверить резерв
с фактической стоимостью. Для параллельных запросов резервы атомарны;
первая версия может выполнять модельные запросы последовательно.

Закрытие HTTP-соединения или остановка Docker не гарантируют отмену генерации
и биллинга у provider. Строгая финансовая граница возможна только при
достоверной верхней оценке, актуальных тарифах и соблюдении provider лимита
output. Эти условия должны быть проверены при интеграции. В отчёте различать
остановку дальнейших запросов и подтверждённую отмену уже начатого запроса.

**B-06.** Неизвестная стоимость/usage имеет статус `unknown`, а не ноль.
Не начинать следующий платный запрос, пока расход нельзя ограничить;
сохранять неопределённый расход и резерв отдельно. При timeout billable
попытку нельзя забывать или освобождать её резерв как заведомо бесплатную.
Недоступность обязательного аудита запрещает дальнейшие платные вызовы.

**B-07.** `doc_review` не обходит лимит. Новый ручной запуск имеет новый
лимит одного запуска, поэтому не ограничивает суммарные траты PR или дня.
Дополнительный `YDBDOC_REVIEW_DAILY_BUDGET_RUB` и общий бюджет с переводами
предлагаются к согласованию. Дневной интервал при введении такого лимита:
Europe/Moscow; при параллельных PR нужны атомарные общие резервы.

**B-08.** При отмене GitHub Actions сохранять уже известные расходы и
незавершённые резервы вне контейнера. Publisher должен публиковать итог
через отдельный финализирующий механизм; нельзя полагаться исключительно
на завершение Python или `always()` после принудительного уничтожения runner.

## 7. Результат проверки

**O-01.** Предлагается один обновляемый общий комментарий и один актуальный
Check `YDB documentation policy review` на head SHA. Отчёт включает состояние,
проверенные файлы, coverage, замечания по приоритету, сумму/лимит и указание
неполноты. Пользователю доступна команда перезапуска через `doc_review`.

**O-02.** Замечания, относящиеся к строкам diff, публиковать как review comments;
замечания к структуре статьи или недоступным строкам помещать в общий отчёт
с полным путём. Suggestions допускаются только после проверки точной привязки.
Старые замечания не дублировать, устранённые обозначать как исправленные.
Для дедупликации сохранять стабильный ключ PR/rule/path/контекст нарушения.

**O-03.** Результаты различают `clean`, `findings`, `waiting_for_approval`,
`no_reviewable_changes`, `budget_exceeded`, `budget_insufficient`,
`cost_unknown`, `scope_limit_exceeded`, `superseded`, `cancelled`,
`infrastructure_error` и неполную coverage. Только завершённая проверка
всей применимой области может считаться `clean`.

**O-04.** В первой версии предлагается информационный Check без обязательного
branch protection. При дальнейшем включении блокировки согласовать приоритеты,
которые дают failure, и обработку неполной проверки. Бюджетная остановка и
ошибка модели никогда не отображаются как отсутствие нарушений.

**O-05.** Хранить метаданные и расходы в YDB с отдельным типом запуска
`doc_review`. TTL полных текстов, срок хранения финансового аудита и права
чтения согласовать отдельно. Публичные комментарии и artifacts не содержат
секреты и полные model transcripts.

## 8. Приёмочные сценарии

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| A-01 | Collaborator открывает PR с документацией, в том числе из fork | Автоматическое ревью; проверяется head этого PR |
| A-02 | Внешний автор открывает PR | Ожидание; ноль вызовов модели |
| A-03 | Уполномоченный сопровождающий ставит `ok-to-test` | Одно ревью разрешённого head |
| A-04 | PR-check успел удалить `ok-to-test` | Сохранённое разрешение работает для того же SHA |
| A-05 | Внешний автор обновляет head | При предлагаемой политике ожидание нового разрешения |
| A-06 | `doc_review` поставлена после полного ревью | Новый запуск на актуальном head; метку можно поставить снова |
| A-07 | `doc_review` без допуска внешнего автора | Платный запуск не начинается |
| A-08 | Нерелевантная метка или повторная доставка события | Нет дополнительных вызовов и отмены активного ревью |
| A-09 | Новая версия PR появляется во время платного ревью | Старая попытка остановлена; её расходы сохранены; новая ждёт 300 секунд |
| A-10 | PR изменяет свои правила или содержит инструкции для бота | Используется доверенный rules SHA; код PR не исполняется |
| A-11 | Лимит отсутствует, некорректен или равен нулю | Ноль вызовов модели; понятная причина |
| A-12 | Следующая платная попытка/повтор не помещается в бюджет | Она не начинается; partial report без clean |
| A-13 | Фактическая сумма ответа превысила лимит | `budget_exceeded`; нет следующих вызовов |
| A-14 | Usage отсутствует или timeout оставил неизвестную стоимость | `unknown`; ноль не подставляется; следующие вызовы запрещены |
| A-15 | Нарушения правил 1–15 на размеченных примерах | Верные ID/приоритеты/пути; неподдержанные проверки явно отмечены |
| A-16 | Модель выдумала путь, строку или цитату | Такое замечание не публикуется как подтверждённое |
| A-17 | PR изменил только код вне документации | Модель не вызывается |
| A-18 | Файл/контекст превышает лимит; список файлов неполон | Явная остановка; нет молчаливого усечения |
| A-19 | Повторное ревью исправленного PR | Нет дубликатов старых замечаний; отчёт актуализирован |
| A-20 | Принудительная отмена runner | Потраченные суммы/резервы сохранены; результат неполный |
| A-21 | Тег action перенесён на новый коммит с опубликованным образом | Следующий запуск использует новую версию; consumer CI не изменён; фактические SHA/digest записаны |
| A-22 | Тег возвращён на предыдущий рабочий коммит | Следующий запуск использует предыдущую версию и её образ без изменения CI |
| A-23 | Коммиты приходят в t=0, t=60 и t=120 | Модель не вызывается до t=420; проверяется только последний head |
| A-24 | Head меняется на границе окончания ожидания | Старый worker не запускается; новое ожидание 300 секунд |
| A-25 | PR закрывается или становится draft во время ожидания | Ожидание прекращается; ноль вызовов модели |
| A-26 | API состояния PR недоступен после ожидания | Платного запуска нет; infrastructure error |

Дополнительно подготовить согласованный корпус корректных и нарушающих правила
примеров из реальных PR, в том числе #55451 как проверку загрузки policy.
Числовые цели по ложным срабатываниям и полноте назначаются после разметки корпуса.
Тесты CI, Docker, модели, бюджета и GitHub API сначала выполняются без реальных
платных запросов; оплачиваемый пилот имеет отдельный малый лимит.

## 9. Этапы реализации и открытые решения

1. Согласовать [открытые вопросы](knowledge/doc-review/open-questions.md),
   область проверки и корпус примеров. Утвердить репозиторий хранения.
2. Добавить загрузчик нормативных правил, контракт findings и формальные
   проверки; общий конфиг модели и бюджет на каждую попытку.
3. Создать Docker-образ, CLI `review`, аудит, идемпотентность и publisher.
4. Добавить небольшой consumer workflow в ydb с корректным допуском и
   постоянным тегом action; фактические SHA запусков сохранять в аудите.
5. Провести ограниченный информационный пилот, измерить качество/стоимость.
   Решение о блокировке merge принимается по результатам пилота.

До согласования этот файл является самостоятельным черновиком нового режима.
Он не подтверждает реализацию, запуск CI, выпуск контейнера или изменение
действующих правил документации.
