# Проверка необходимости перевода по языковым парам

## Решение 2026-10-28

Классификация выполняется отдельно для каждой Markdown-пары. Наличие RU и EN
само по себе не доказывает, что перевод актуален. Изменение обоих файлов тоже
не является достаточным основанием для skip: изменения могут быть частичными
или противоречащими. Сравнивается смысл именно изменений.

Промпт содержит Git-факты, изменения и целые затронутые Markdown-блоки с
контекстом заголовков. Текущие файлы не повторяются в отдельном pairs-массиве.
Для need_context допустим один повтор: полные текущие статьи непрерывным
current_text, а при превышении бюджета целые соответствующие разделы с
подразделами. Для каждой дельты проверяется наличие кандидата. Позиции блоков
не используются для поиска разделов в этом fallback. Нет соответствия:
need_context без пустого model retry. Разделы не разбиваются.
Неделимый слишком большой фрагмент не обрезается молча: решение остаётся
неопределённым и выполнение требует пояснения пользователя.

Решения: no_translation, ru_to_en, en_to_ru, need_context, conflict.
Последние два после исчерпания расширения создают checkpoint с причиной пары.
Невалидный ответ не считается разрешением пропустить перевод.

## Выполнение и продолжение

По решениям строятся группы направлений. Каждая группа использует прежние
операции Git, metadata, dependency discovery и перевод изменённых фрагментов.
Итог объединяется в один кандидат с проверкой уникальности outputs. Агрегат
mixed не назначает язык отдельному документу: используются локали его пары.
Решения сохраняются в source inventory checkpoint и восстанавливаются без
повторной классификации. Старые checkpoints остаются читаемыми.

Если все пары согласованы и нет работы с ресурсами, job завершается успешно,
пишет понятный комментарий и не вызывает translator/publication. Исправления
отсутствующей части перевода не должны затирать согласованную часть target.

## Частично выполненный перевод

Для выбранной пары, где в исходном PR изменены обе локали, прежние
insert-only append / delete-only noop эвристики не используются: они могли
дублировать уже переведённый абзац или оставить неперенесённое удаление.
Модель получает source delta и текущий target и предлагает точные замены
`old` -> `new` в target. Python проверяет уникальность каждого old,
непересечение диапазонов и запрещает замену целого документа. Остальные
байты, включая переводы строк, сохраняются. Неоднозначный ответ повторяется
один раз, затем ошибка без возврата к опасному append/noop или whole-file.
Запрос/ответ ограничены 128 КиБ, ответ модели 16384 токенами, список 128 заменами.

## Большие пары: проверка по частям

Проверка #55293 обнаружила oversized changelog после исправления Markdown URL.
Списки разбираются по целым пунктам верхнего уровня, сохраняя вложенные пункты,
продолжения и блоки кода. В контексте остаются заголовки выбранных разделов и
количество пропущенных разделов; отсутствие показанного текста не доказывает
его отсутствие в документе.

Если полный запрос с резервом ответа превышает бюджет токенов, набор изменений обеих локалей делится
пополам до ограниченных запросов. Нельзя пропустить дельту или обрезать пункт.
Каждая часть получает собственное семантическое решение и ограниченный retry.
Итог no_translation требует no_translation всех частей. Одно направление
в сочетании с no-op остаётся этим направлением; разные направления дают
conflict; любая оставшаяся неопределённость блокирует no-op и перевод.
Крупная новая страница или неделимый фрагмент сверх лимита остаётся need_context.

Направления ограничены локалями фактических дельт текущей части запроса.
RU-only допускает ru_to_en, EN-only допускает en_to_ru; текущий текст другой
локали является доказательством, а не источником нового изменения. Ограничение
применяется в JSON schema и при разборе ответа. Недопустимое направление
повторяется один раз, затем conflict. Новая страница считается исходной дельтой.

При делении большого набора дельты перемежаются по порядку изменения и локали,
чтобы не создавать отдельную часть для всего EN и отдельную для всего RU.
Порядковые номера используются только для упаковки, не доказывают соответствие
переводов. Набор дельт и правила агрегации остаются прежними.


## Подбор контекста по изменённым строкам, #52520

Сначала ищем anchors (inline code и ссылки) из каждой изменённой строки.
Среди найденных совпадений предпочитаем anchors с наименьшим числом блоков
в целевой статье. Все равнозначные совпадения сохраняем; частота является
подсказкой для поиска, не доказательством соответствия перевода.
Если строка не дала совпадений, используем anchors её затронутых блоков.
Fallback независим для каждой строки, чтобы совпадение одного изменения
не скрывало prose-only изменение другого раздела.

Целые before/after blocks, собственные дельты обеих локалей, соседние кандидаты
по позиции и ограниченное расширение разделами сохранены. Решение no_translation
по-прежнему принимает модель. Нет списка специальных исключений RATE/GAUGE.

Регрессия использует полные исходные снимки PR52520 в tests/fixtures/pr52520.
Запрос на тех же данных уменьшился с92898 до21872bytes и содержит обе дельты
вместе. Дополнительно проверены перестановка блоков, равнозначные совпадения
и независимый fallback для нескольких изменений.

## Целые таблицы и объяснение до решения, 29 октября

Порог64KiB удалён. Production preflight использует RecordedModels.prepare_request
и ту же сериализацию openai_payload, что транспорт. Вход оценивается консервативно
по полному wire JSON (1UTF-8byte как верхняя оценка token), плюс полный резерв4096.
Для classifier применяем окно262144, фактически сообщённое endpoint в аудите
context400; документированный максимум модели1M не гарантирует окно маршрута.
Это не точный tokenizer и не утверждение равенства байтов и реальных токенов.
Резерв/окно проверяются до вызова, только при нехватке включается прежний batching.

Изменён prompt: сравнение, reason, решение. Provider сортирует поля schema
алфавитно, поэтому action переименован в translation_action в wire schema,
чтобы reason генерировался первым. Все19реальных ответов подтвердили порядок
key,reason,translation_action. Parser поддерживает прежний action без изменения
смысла; оба поля одновременно не допускаются. Дополнительного judge нет.
Примеры учат отличать исправленную ссылку/локализованный якорь от отсутствующего
перевода. Код не извлекает решение регуляркой из reason.
